# What 1.0 is waiting for

Status: the standing list. Started 2026-09-17, the day two production stacks
first shared a state channel.

Kept here rather than as a milestone in a tracker because the answer is not a
date and the list is mostly other plans. Tick things off it; do not add a
deadline to it.

## 1.0 is a quiet week, not a feature list

`VERSION` went 0.9.1 on 14 Sep to 0.9.8 on 17 Sep -- eight builds in four
days, and nearly every one fixed something that only existed in live use: the
lazy cursor in `pin_pending`, one change-log line posted seven times, reopens
that had never once worked in five months, and the shared rate-limit bucket
that broke the second laptop on its first day. That is the ordinary shape of a
tool three days into production. It is also exactly what 1.0 cannot look like.

So the gate is the rate, not the list below: **the first week in which nothing
forces a build.** Everything here is a thing that would otherwise force one,
or a thing that cannot be judged until the rate settles.

Today is not close. Two fixes went in on 17 Sep and the second one
(`ernie_changelog`'s unpaced `BATCH`) was found by going looking for the same
shape elsewhere, not by it biting. A list that is still being *discovered* is
not a list being worked through.

## The one that gates the others

**The two-machine setup has to run clean on production for a week.** It went
up on 17 Sep and broke the same day: both stacks share the bot, so they share
one rate-limit bucket, every state publish 429'd, and a card moved on one
board took six minutes to reach the other. `WRITE_PACE` is the fix and it is
in `development`; neither laptop has it, because both run installed 0.9.8.

- [ ] Cut 0.9.9 and install it on both machines.
- [ ] Run phase 5 of the preflight -- the four conflict tests, which have
      never been run: both move the same card, one closes while the other
      edits, both edit the same ticket, count the announcements on a Discord
      closure. These are the least exercised paths in the project and a
      second real laptop is the only way to reach them.
- [ ] A week of two boards with no build cut for them.

`plans/changelog-per-machine.md` is parked behind this and says so: one of its
two open questions can only be answered by watching two real boards disagree.
It does not need to ship for 1.0, but it cannot be *decided* before this.

Julian has had the exe since 0.9.5 and has not run it. Every piece of
feedback so far -- the close-thread rule, the work-item guard, the card issue
wording -- came from him looking at somebody else's screen. A 1.0 whose second
user has never opened it is a 1.0 in name only, and his first real session
will produce a list.

- [ ] Julian runs his own stack for a working week.
- [ ] Whatever that produces is triaged into this file before 1.0 is cut.

## Decisions that get harder after 1.0

Three things are cheap to change now and expensive once a version number has
promised not to move them.

- [ ] **`MIN_BERT`.** It is `0.9.0` and is raised by hand, on a release that
      actually breaks something. Shipping 1.0 with a 0.9.0 floor lets every
      stale board go on writing to the shared channel. Decide at the cut
      whether 1.0 is the release that breaks something; if it is not, leaving
      it alone is a real answer and should be a written one.
- [ ] **`ANNOUNCE_CLOSURES` is misnamed.** It gates reopens too, and has
      since reopens started working. The name is in `ernie-test.env.example`,
      `TESTING.md`, `ernie_load.py` and the installed env on both production
      machines, so renaming it means editing files on two laptops by hand --
      annoying now, and a breaking change for anybody else's install later.
      Rename it before there is anybody else, or accept the name for good.
- [ ] **`FORMAT_VERSION`.** Not `VERSION`, and nothing about 1.0 obliges it to
      move. Confirm that at the cut rather than discovering later that the
      release quietly changed the wire format.

- [ ] `README.md`, `TESTING.md`, `SetupGuide.rtf` and the four files in

hour something broke.

## Not in 1.0

Worth naming, so that they stop being weighed every time this file is read.

The Jira client list is built and inert unless configured; it does not need to
be switched on in production for 1.0. Bert's WAL strip exists and has never
been drawn in anger, which is the correct amount of times for it to have been
drawn -- it is not evidence of anything untested, it is the alarm not going
off. The one-machine rule on `CHANGELOG_CHANNEL_ID` is liftable and does not
need lifting.

## How you know

Not a checklist item, because it is a judgement and it should be made
deliberately: look at the git log for the fortnight before the cut. If every
build in it was a feature or a rewording, it is 1.0. If any of them was
something breaking in front of somebody, the week starts again.
